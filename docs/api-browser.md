# Браузер API

[← к README](../README.md)

У мододела нет ни документации по клиенту, ни поиска по нему, а загрузчик модов отдаёт моду
ровно **шесть колбэков**: `onAccountShowGUI`, `onAccountBecomePlayer`,
`onAccountBecomeNonPlayer`, `onAvatarBecomePlayer`, `onConnected`, `onDisconnected`. Всё
остальное добывается подпиской на события клиента или монкипатчем. Экран «Браузер API»
отвечает на вопрос «что и где мне перехватить».

Экран работает по дереву декомпилированных исходников вашего клиента. Как его получить —
в [Исходниках клиента](client-sources.md). Индекс строится в фоне при открытии экрана.

![Браузер API: поиск по символам](api-browser.png)

Панели экрана: **поиск**, **дерево** модулей, каталоги **события**, **сервисы** и **патчи**.
Справа — исходник выбранного символа, «где это вызывается» и сниппеты.

## Поиск по символам

Поиск понимает точное совпадение, префикс, акроним по горбам CamelCase (`pushmsg` →
`pushMessage`), нечёткое совпадение и запрос **с точкой** — той формой, которой API называют
и которую кокпит сам показывает в заголовке карточки: `SystemMessages.pushMessage`,
`_PlayerEvents.onAvatarReady`, `dependency.instance`, `gui.SystemMessages`. Запрос режется по
последней точке: хвост ранжируется как имя, а голова обязана найтись в квалифицированном
имени или в модуле файла.

Результаты ранжируются: интерфейс из `skeletons/` идёт выше реализации. Два слоя шума по
умолчанию спрятаны за чипами: сгенерированные таблицы (`gui/impl/gen`, `Scaleform/locale`)
за **«+ ресурсы»** и вендорный код (`site-packages`, `common/Lib`) за **«+ stdlib»**. Если
имя живёт только в скрытом слое, кокпит не пишет «ничего не найдено», а говорит, где оно
есть, например: «в игровом коде ничего; 2 в сгенерированных — включите фильтр над списком».

Рядом с именем показано, в скольких местах клиента оно объявлено. Если метод объявлен в
нескольких классах, монкипатч одного из них «не срабатывает» — и это видно сразу.

Отдельным видом символа (`svc`) индексируются **модульные синглтоны** — присваивания вида
`g_playerEvents = _PlayerEvents()` на нулевом отступе. `def` или `class` с таким именем в
клиенте нет, а подписка мода пишется именно через них
(`g_playerEvents.onAvatarReady += handler`). Без этого вида поиск главного имени отвечал бы
«ничего не найдено».

## Исходник

Файл открывается прокрученным к строке объявления, строка подсвечена. Кнопки: **открыть в
VS Code**, **копировать импорт**, **вирт. путь** (`scripts/client/gui/SystemMessages.py` —
тот, что печатает traceback) и **путь на диске**. Кадр traceback с экрана лога открывается
здесь одним действием.

## Где это вызывается

Панель «где это вызывается» каждый раз заново проходит по всему дереву. Попадания размечены
по виду: объявление, вызов, `+=`/`-=` (подписка на событие), чтение атрибута, импорт,
строковый литерал, комментарий. Границы слова включены всегда: совпадения внутри других
идентификаторов отбрасываются, иначе список тонет в однокоренных именах.

Чип **«приёмник»** уточняет запрос до вида `g_playerEvents.onAvatarReady`. Приёмник берётся
только оттуда, где он настоящий, — из записи каталога (глобальный синглтон, слот боевой
сессии, атрибут сущности). **Имя класса-владельца приёмником не является**: в исходниках не
пишут `ISettingsCache.update(...)`, пишут `self.update(...)` и `settings.update(...)`, так что
уточнение по классу давало бы ноль попаданий. Поэтому символ индекса ищется голым именем, а
сузить список помогает строка **«частые приёмники»** под заголовком панели. Если уточнение
всё-таки дало ноль, кокпит сам повторяет запрос голым именем и пишет об этом.

Смена выделения в списке запускает поиск ссылок с той же задержкой 150 мс, что и набор
текста: каждый такой поиск — полное перечитывание дерева, и без задержки пролистывание
стрелками давало бы рывки интерфейса.

## Каталог событий

![Каталог событий: запрос «бой»](api-browser-events.png)

Каталог строится из исходников, курируемых списков нет: событие — это `self.onX =
Event.Event()`. Для каждой записи показаны путь доступа из мода
(`from PlayerEvents import g_playerEvents`, `dependency.instance(IBattleSessionProvider)`,
`BigWorld.player().arena`), сигнатура, восстановленная по местам возбуждения, число подписок
в самом клиенте и два предупреждения, которые дороже всего остального:

- **`Event`, а не `SafeEvent`.** Исключение из обработчика уходит в клиент
  (`common/Event.py` логирует его и бросает дальше) и способно уронить бой. Это свойство
  почти всего каталога, а не отдельной записи, поэтому оно написано один раз над списком и
  повторено в карточке выбранной записи и в шапке сниппета;
- **владелец существует только в бою.** Вне боя `sessionProvider.shared.<слот>` равен `None`.
  В строке списка такие записи помечены «только в бою».

**Список отвечает и тому, кто не знает слов клиента.** Без этого каталог из тысячи записей
отвечал бы только тому, кто знает ответ заранее:

1. шесть колбэков загрузчика закреплены сверху и помечены значком `загрузчик`;
2. совпадения по ИМЕНИ идут выше совпадений по пути доступа и пути файла;
3. маленькая карта «слово человека → слово клиента» (34 ключа: `бой`/`battle` → `arena`,
   `вошёл` → `onAvatarBecomePlayer`, `ангар` → `lobby`, `урон` → `onHealthChanged`…).
   Карта ничего не добавляет в каталог и ничего не утверждает о клиенте: она только
   маршрутизирует запрос, а подмена видна в строке состояния («по запросу «бой» искали также:
   arena, onAvatarBecomePlayer…»).

## Каталог сервисов

Всё, что лежит в `client/skeletons/**`, упорядочено по числу обращений
`dependency.instance` / `@dependency.descriptor` в клиенте. Алфавит здесь бесполезен:
сотня интерфейсов из одного `skeletons.gui.game_control` похоронила бы нужные шесть.

## Каталог патчей

Что на практике патчат моды: курируемая таблица из 252 пар «класс.член», собранная по
нескольким распространённым модам и зашитая в кокпит. Чужие `.mtmod` вживую кокпит не
разбирает. Зато **каждая запись проверяется по индексу вашего клиента**, и то, чего в нём
нет, помечается «патч мёртв». «Этого в вашей версии больше нет» — тоже ответ, и именно он
спасает при обновлении игры.

Если дерево исходников не указано, проверять не по чему, и панель пишет это прямо: «по
клиенту НЕ проверено: дерево исходников не указано». Иначе все записи молча читались бы как
«есть в вашем клиенте».

## Сниппеты

Кнопка кладёт готовый код в буфер обмена и показывает его целиком: вслепую в проект он не
уезжает. Три шаблона плюс **«рекомендуемый»**, который выбирает сам каталог:

- **подписка** — флаг однократности, отписка в `fini()`, тело обработчика целиком в
  `try/except`. Если владелец живёт только в бою, подписка становится двухступенчатой
  (через `g_playerEvents.onAvatarBecomePlayer`), потому что вне боя владельца нет;
- **монкипатч** — оригинал берётся через `getattr` в момент установки и вызывается первым,
  свой код в отдельном `try/except`, реестр на уровне модуля делает патч идемпотентным, а
  `fini()` гасит флаг вместо `setattr` обратно: поверх вашего патча мог сесть другой мод;
- **сервис** — `dependency.instance` с проверкой всех трёх режимов отказа.

Имя логгера в сниппете (`logging.getLogger('mod_<id мода>')`) берётся из открытого проекта.
Подписку и сервис кокпит строит только по каталогу (там резолвер владельца, сигнатура и
предупреждения), поэтому, если каталоги ещё не строились, кнопка сначала строит их сама.

Код сниппетов и всё, что кокпит вставляет в ваш мод, лицензировано по 0BSD (см.
[README](../README.md#лицензия)).

## Пример: что перехватить, чтобы узнать о входе в бой

1. Экран **«Браузер API»** → панель **«события»**.
2. В поле фильтра — **`бой`**. Список сужается, сверху идут `onAvatarBecomePlayer` (со
   значком `загрузчик`), `onAvatarReady`, `onArenaPeriodChange`. В строке состояния видно,
   чем на самом деле искали: `arena`, `onAvatarBecomePlayer`, `onAvatarReady`.
3. Щелчок по записи: в центре открывается её объявление, справа «где это вызывается»
   показывает, как на это событие подписываются в самом клиенте, а в карточке —
   предупреждение про `Event`/`SafeEvent`.
4. Кнопка **«рекомендуемый»** кладёт в буфер готовую подписку. Для события боевого владельца
   (например, `onArenaPeriodChange` через `BigWorld.player().arena`) подписка сразу
   двухступенчатая.

## Как устроен индекс

Ни SQLite, ни полнотекстового движка: индекс живёт в памяти и строится в фоне, полный
параллельный проход по дереву занимает доли секунды.

Разбор — **лексический, построчный, без состояния между строками**. Это требование самого
корпуса, а не упрощение: uncompyle6 печатает часть файлов с неэкранированным апострофом
внутри строкового литерала, и парсер, считающий кавычки, молча съел бы на них остаток файла.
Ещё одна ловушка — концы строк: файлы дерева в CRLF, и если срезать `\r` после вычисления
отступа, а не до, из индекса пропадают все методы.

Каталоги событий, сервисов и патчей строятся лениво, при первом открытии своей панели, с
индикатором и отменой. Индекс символов и каталоги пока читают дерево независимо друг от
друга; это видно по памяти процесса.

### Пример замеров на одной машине

Дерево клиента 1.44 (8052 файла, 59 МБ), процессор с 28 логическими ядрами. На другой машине
и другой версии клиента числа будут другими.

| что | сколько |
|---|---|
| построение индекса | 0.25–0.4 с |
| символов в индексе | 166 574, из них 117 901 `def`, 1027 событий `Event.Event()`, 138 модульных синглтонов |
| поиск символа | доли миллисекунды; худший случай — запрос из двух букв (`on`), около 17 мс |
| «где это вызывается» для `pushMessage` | 189 попаданий в 82 файлах, около 50 мс |
| построение трёх каталогов | около 0.5–0.6 с |
| каталоги | 1027 событий, 215 сервисов, 252 записи патчей (из них 49 «патч мёртв») |
| управляемая куча под индексом | около 27 МБ |
| рабочий набор приложения после прохода по всем панелям | около 400 МБ |
