# Переход на новую версию клиента

[← к README](../README.md)

После обновления игры `paths.xml` смотрит в новый каталог `mods\<версия>`, а свои моды
остаются в каталоге прошлой версии — и в игре их просто нет. Экран «Моды» замечает это сам
при каждом чтении каталога и показывает баннер «Клиент обновился: 1.45.0.0 → 1.46.0.0…» с
кнопкой **«Перейти на 1.46…»**. Распознавание только читает.

![Окно «Переход на новую версию клиента»](client-migration.png)

## Что считается «остались в прошлой версии»

**Прошлая версия** — самая новая из более старых каталогов `mods\`, в которой есть хоть один
СВОЙ мод. Связь мода с проектом та же, что у «своих» строк экрана «Моды»: `<id>` из
`meta.xml`, а у архива без `meta.xml` — имя файла `<id>_<версия>.mtmod`. Во втором случае
побеждает самый длинный `<id>`, чтобы `ru.local.clock_lite_1.0.mtmod` не достался проекту
`ru.local.clock`. Каталоги без своих модов пропускаются: после нескольких обновлений там
копятся старые версии чужих модпаков.

**К переносу** — свои ВКЛЮЧЁННЫЕ моды, которых в активном каталоге нет ни в каком виде (по
одному файлу на мод, самый свежий). Выключенные в прошлой версии показываются только для
сведения и не переносятся: выключал их человек.

## Что происходит по кнопке «Начать переход»

### 1. Исходники новой версии

Если рядом с текущим деревом (`wotSrcDir`) уже лежит `wot-src-1.46` (или
`wot-src-1.46.0.0`) с исходниками, берётся оно. Иначе кокпит извлекает дерево сам:

- `scripts.pkg` игры читается как ZIP (игра только читается), а `client/`, `client_common/`
  и `common/` гонятся через uncompyle6 параллельно, по ядрам;
- рядом записываются модули остальных `*.pkg` клиента (`.cockpit-extra-modules.txt`: по ним
  preflight знает, что эти модули существуют) и отметка версии (`.cockpit-client.json`);
- дерево пишется во временный каталог и встаёт на место только целиком. Отмена и сбой не
  оставляют полудерева, а декомпиляция, не давшая ни одного полностью разобранного файла, —
  это ошибка с первой причиной, а не пустое «готовое» дерево;
- если готовое дерево не удаётся переименовать (файл в нём держит антивирус), работа не
  удаляется: путь временного каталога будет в тексте ошибки.

Где кокпит ищет Python с uncompyle6 и как его поставить — в
[Исходниках клиента](client-sources.md#декомпилятор). Если Python с декомпилятором не
найден, окно предлагает поставить его или положить готовое дерево `wot-src-<версия>` рядом
с текущим.

**Как кокпит понимает вывод uncompyle6.** Успехом файла считается только строка
`# okay decompiling` в выводе: код возврата uncompyle6 — 0 и тогда, когда разбор модуля
упал. «Частично» — только когда декомпилятор сдался на вложенной функции, уже выведя текст
модуля (`# Deparsing stopped due to parse error`); такой файл получает пометку в первой
строке, а отладочный вывод парсера (сотни строк правил грамматики перед текстом)
вырезается. Ошибка разбора модуля или класса и неподдерживаемый байткод — «не вышло»: в их
выводе нет ни строки исходника. Такие модули записываются поимённо в
`.cockpit-failed-modules.txt`. В игре они есть, поэтому проверка не выдаёт их за удалённые,
а preflight — за несуществующие (`WOT002`). Этот список читается и у базы сравнения: модуль,
который в прошлой версии не декомпилировался, а в новой исчез, — «модуль удалён», а не давняя
ошибка.

**Две мелочи, о которые спотыкается извлечение.** Пустые каталоги `py-dis-*`, которые
uncompyle6 оставляет на каждый файл, ложатся в собственный временный каталог и удаляются
вместе с ним. Копии `.pyc` для декомпилятора лежат плоско, под номерами, в коротком
временном каталоге: Python без включённых длинных путей Windows не открывает файл длиннее
260 символов, а глубокие пути клиента рядом с глубокой целью за этот предел выходят.

Каталог с нужным именем, но без исходников этой версии, не затирается — окно скажет, что
его надо убрать. Если текущее дерево лежит в папке игры, новое туда не кладётся: окно
попросит указать дерево вне её.

Пример на одной машине: извлечение `scripts.pkg` клиента 1.46 (около 8100 файлов) заняло
около четырёх минут.

### 2. Проверка каждого своего мода

Индексы обеих версий строятся по разу. **База сравнения** — дерево именно прошлой версии
(`wot-src-1.45` рядом с текущим; версия — по отметке кокпита или по имени каталога), и в нём
действительно есть исходники (пустой `client\` с правильным именем базой не считается).
Только с такой базой «совместим» считается доказанным.

Мод проверен не до конца — и переносится только вручную, — если он:

- импортирует модуль, сравнить который не с чем: его нет в базе, он не декомпилировался в
  новой версии (даже если и в старой тоже) или переехал в дополнительный пакет, откуда кокпит
  берёт только имена;
- упоминает функцию, которую uncompyle6 не разобрал в одной из версий.

В вопросе перед переносом названо, что именно не сравнено.

Без базы нужной версии база — текущее дерево из настроек, если оно не новой версии
(сравнение что-то покажет, но доказательством не считается), а нет и его — только preflight
по новой версии. В обоих случаях **автоматического переноса нет**: строки не отмечаются,
перенос — вручную и с вопросом. Дерево той же или более новой версии, чем клиент, базой не
бывает никогда: с ним «ничего не изменилось» всегда.

**Блокирует автоматический перенос:**

- исчез модуль клиента, который мод импортирует (не переехал в дополнительный пакет и не
  просто не декомпилировался);
- в изменившемся модуле исчезли функция, класс, метод, событие, константа или синглтон
  (`g_*`), которые мод упоминает — в коде или строкой-идентификатором вроде
  `('showShotResults', …)`. Метод учитывается, только если мод упоминает его класс или
  синглтон этого класса: `g_playerEvents = _PlayerEvents()`, значит
  `g_playerEvents.isPlayerEntityChanging()` зависит от `_PlayerEvents`, а `update` у сотни
  классов — не повод для тревоги. Событие учитывается всегда, когда мод упоминает его имя
  (`onArenaPeriodChange`). Закрытый метод — и в искажённом виде
  (`_PlayerAvatar__onSiegeStateUpdated`), в котором его перехватывают;
- у такой функции или метода поменялась сигнатура: перехваты берут аргументы по позиции;
- появилась новая ошибка preflight, которой на прошлой версии не было;
- исходники новой версии пусты — проверять не по чему (кокпит на такое дерево и не
  переключается).

**Заметки, которые перенос не блокируют:** какие из импортируемых модулей изменились, новое
значение упомянутой константы, новые предупреждения preflight. Давние замечания мода на
переход не влияют — сравнивается только новое. Служебные строки декомпилятора (путь к
`.pyc`, версия uncompyle6) изменением модуля не считаются.

### 3. Переключение на новое дерево

`wotSrcDir` в настройках, браузер API, preflight и маппер traceback дальше работают по
новому дереву.

### 4. Перенос

Если стоит галочка **«Сразу перенести всё, что проверку прошло»** (по умолчанию стоит),
совместимые моды переносятся сразу.

Ставится **сборка своего проекта**, а не копия старого файла: проверялись исходники, значит,
и в игру идёт их сборка. Свежая сборка в `dist\` берётся как есть; устаревшую или
отсутствующую `build.py` собирает заново (без `--install`, вывод — на экране «Сборка и лог»;
«Остановить» в окне снимает и `build.py`). Устаревшей считается сборка, которая:

- старше правок в `src\`;
- содержит файл, исходника которого в `src\` уже нет (удалили вторую точку входа и не
  пересобрали — по времени оставшихся файлов этого не видно);
- не читается как ZIP (упаковку оборвали).

В игру пишет служба библиотеки модов, как у «Поставить из dist»: только `*.mtmod`, только в
каталог новой версии, не при запущенной игре; файл с тем же именем не перезаписывается;
каждая операция — в журнал экрана. Выключать «прежние копии» при переносе нечего (иначе мод
не ждал бы переноса), поэтому это правило здесь выключено. На экране «Моды» то же правило
узнаёт мод по `<id>` из `meta.xml`, а у архива без `meta.xml` — по `<id>` из имени файла
целиком, поэтому установка `ru.local.clock` не выключает `ru.local.clock_lite`.

## Проблемные моды

Мод с проблемами не отмечается; находки показаны в его строке с местом в моде и в клиенте.
Его можно отметить и перенести кнопкой **«Перенести отмеченные»** — после отдельного вопроса
со списком проблемных.

Каталог прошлой версии не меняется никогда: откатиться — значит просто вернуть прошлую
версию игры.

Проверка — сито, а не доказательство. Связь «объект → класс» без исполнения кода не
установить, поэтому атрибуты объектов, полученных вызовами (`BigWorld.player().arena…`),
сверяются, только если мод импортирует модуль, где они объявлены. Задача проверки — не
пропустить автоматически то, что сломано заметно.

## Что проверено

`ClientMigrationCoreTests` — версии, деревья, распознавание (только чтение: сверяется
отпечаток каталогов), моды с общим началом `<id>`, след мода, все виды находок (синглтоны,
события и методы через синглтон, закрытые методы в искажённом виде, пустой индекс, пустая
база с правильным именем, модуль, которого нет в базе), разбор вывода uncompyle6 по форме
настоящего (с отладкой парсера, с неподдерживаемым байткодом) и извлечение из фейкового
`scripts.pkg` с подменённым декомпилятором (частичные, неудачные, ни одного целого файла,
отмена, занятый каталог, непереименуемое готовое дерево, глубокая цель).

`ClientMigrationViewModelTests` — окно на фейковой игре с настоящей службой библиотеки:
перенос только совместимого, ручной перенос с вопросом, база неизвестной версии и повторное
открытие, не до конца проверенный мод, цель в папке игры, пересборка устаревшего, сбой
сборки, запущенная игра, отмена, пустое дерево, отрисовка окна без ошибок привязок, баннер
экрана «Моды».
