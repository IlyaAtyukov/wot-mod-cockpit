# Preflight: статический анализ до сборки

[← к README](../README.md)

Для C#-разработчика это «Roslyn-анализатор для мода»: список находок с файлом, строкой,
серьёзностью и объяснением. Разница в том, откуда берутся правила. Компилятор Python 2.7
проверит синтаксис, pyright проверит имена, но ни тот, ни другой не знают, что
**необработанное исключение в `init()` вашего мода закрывает клиент игры**. Каждое правило
ниже опирается на факт из декомпилированного клиента, а не на общие соображения о
хорошем коде.

![Панель Problems](problems.png)

## Панель Problems

Док под лентой лога, как в Visual Studio. Группировка **по файлу**, **по правилу** и **по
важности**; фильтр по подстроке; переключатели уровней (ошибки, предупреждения, замечания).
У выбранной находки — карточка с объяснением «почему это плохо» и три действия:
**открыть в VS Code**, **показать в браузере API** (тот символ клиента, из-за которого
правило сработало) и **скрыть правило** до следующего запуска. Полоса действий закреплена под
прокруткой карточки, а не внутри неё, чтобы кнопки не уезжали из виду; те же команды есть в
контекстном меню списка. Высота дока меняется сплиттером.

Тумблеры **«перед сборкой»** и **«при открытии»** включают автоматический прогон. Заведомо
кривой мод иногда собирают специально, поэтому проверка перед сборкой **не блокирует**: она
показывает первые находки и спрашивает «Собрать всё равно?».

## Правила

22 кода в 20 классах правил: у `UnknownApiRule` три кода — `WOT002`, `WOT003` и `WOT004`.
Серьёзность у большинства правил зависит от места находки: одно и то же нарушение на уровне
модуля закрывает клиент, а внутри обработчика только обрывает чужие моды.

| код | что ловит | серьёзность | на чём основано |
|---|---|---|---|
| `WOT001` | игровая работа на уровне модуля без `try/except` | ошибка / предупр. / замеч. | загрузчик ловит при импорте мода только `ImportError`; дальше исключение доходит до `game.init()`, а там `BigWorld.quit()` |
| `WOT002` | импортируется модуль, которого в вашем клиенте нет | ошибка / предупр. | индекс клиента: `scripts.pkg` плюс модули дополнительных пакетов игры |
| `WOT003` | модуль есть, а имени в нём нет (`from X import Y`) | ошибка / предупр. | тот же индекс плюс экспорты модуля |
| `WOT004` | обращение `X.attr` к несуществующему атрибуту | ошибка / предупр. | тот же индекс; проверяются только имена, привязанные к `import` |
| `WOT005` | `init()`/`fini()` и события загрузчика без `try/except` | ошибка / предупр. | загрузчик при вызове методов мода ловит **только** `AttributeError` |
| `WOT006` | обработчик события без `try/except` | предупреждение | события клиента — `Event.Event()`, а не `SafeEvent`: исключение обрывает перебор подписчиков |
| `WOT007` | монкипатч не вызывает оригинал | ошибка / предупр. | ломает и клиент, и другие моды на том же методе |
| `WOT008` | `getattr` без значения по умолчанию | ошибка / предупр. | переименование атрибута игрой → `AttributeError` во время игры |
| `WOT009` | подписка на игровой синглтон без отписки | предупреждение | `PlayerEvents` объявляет события без менеджера — `EventManager.clear()` их не снимет |
| `WOT010` | петля `BigWorld.callback` без `cancelCallback` | предупреждение | колбэк переживает `fini()` и срабатывает на разрушенных объектах |
| `WOT011` | `addListener` без `removeListener` | предупр. / замечание | `g_eventBus` живёт всю сессию клиента |
| `WOT012` | нет пампинга `python.log` | замечание | клиент сам сбрасывает лог на диск только при `IS_DEVELOPMENT` |
| `WOT013` | `LOG_DEBUG` на релизном клиенте | замечание | на релизном клиенте уровень отладки отключён, вызов ничего не пишет |
| `WOT014` | раскладка точки входа | ошибка / предупр. | загрузчик берёт только `mod_*.pyc` из `scripts/client/gui/mods/`; дерево без `init()`/`fini()` верхнего уровня — библиотека, это предупреждение |
| `WOT015` | не-ASCII без объявления кодировки | ошибка / предупр. | PEP 263; файл компилируется **уже внутри клиента**, `check_py2_syntax.py` этого не ловит |
| `WOT016` | файловая операция по относительному пути | предупреждение | рабочий каталог клиента — не каталог мода |
| `WOT017` | смешивание `str` и `unicode` в тексте для GUI и лога | предупреждение | `UnicodeDecodeError` на кириллице в Python 2 |
| `WOT018` | импорт API чужого мода без `try/except ImportError` | предупр. / замечание | ModsListAPI или ModsSettingsAPI может быть не установлен |
| `WOT019` | приватное имя без учёта name mangling | предупреждение | `__name` внутри класса превращается в `_Class__name` |
| `WOT020` | `print` вместо логирования | замечание | строка уходит в `python.log` без уровня, модуля и вашего тега |
| `WOT021` | `sys.path`/`sys.meta_path` без симметричного отката | замечание | изменённый путь импорта переживает выгрузку мода |
| `WOT022` | имя `def`/`class` верхнего уровня объявлено в файле повторно | ошибка / предупр. | модуль исполняется сверху вниз, живёт только последнее объявление, а `check_py2_syntax.py` отвечает `[OK]` |

`WOT002`–`WOT004` работают, только если указано дерево исходников клиента (см.
[Исходники клиента](client-sources.md)); без него правило молчит. Подавляются заведомо
ложные случаи: импорт внутри `try:` (идиома кроссмодового API), нативные модули движка,
stdlib, модули дополнительных пакетов игры и объявленные внешние зависимости проекта.

## Чему верить

Главный тест правил — **не** «сколько нашли», а `ReferenceTemplate_ProducesNoErrors`: на
эталонном шаблоне мода не должно быть ни одной ошибки **и ни одного предупреждения**.
Ложные срабатывания на исправном коде убивают доверие к анализатору быстрее, чем
пропущенная находка.

Разбор лексический, как и в индексе браузера API, но тройные литералы отслеживаются между
строками. Без этого правила ловили бы примеры кода из докстрингов (в эталонном шаблоне их
сотни строк, и там есть и `BigWorld.callback`, и `getattr(cls, name)`). Содержимое литералов
заменяется пробелами с сохранением длины, поэтому колонка находки совпадает с колонкой в
исходнике.

Пример на одной машине: анализ эталонного шаблона (3 файла, около 1400 строк) занимает
десятки миллисекунд; крупный модпак из 163 файлов и 31 тыс. строк — около половины секунды.

## Pyright как линтер

Разовый запуск `pyright` на коде мода. Его JSON-вывод разбирается в те же находки панели
Problems с кодами вида `pyright:reportMissingImports`. Это не LSP и не фоновый сервер:
кнопка → процесс → отчёт.

Фича по умолчанию **выключена** (галочка **«pyright»** в панели). Шума на исправном коде нет,
но каждый запуск — это внешний процесс Node, а preflight идёт автоматически при каждом
открытии проекта и перед каждой сборкой.

**Где pyright ищется** — по порядку:

1. `pyrightPath` в `settings.json`: `…\node_modules\pyright\index.js` (запустится через Node)
   или обёртка `pyright.cmd`/`pyright.exe` от `npm -g`, yarn, pnpm или pip (`.cmd`/`.bat`
   запускаются через `cmd.exe /c`);
2. необязательная локальная установка в шаблоне мода:
   `<шаблон>\.scratch\pyright-test\node_modules\pyright\index.js`;
3. `node_modules\pyright\index.js` рядом с кокпитом или выше;
4. `pyright.exe` или `pyright.cmd` в `PATH` (pip, `npm -g` с другим префиксом, scoop, volta,
   nvm);
5. `%APPDATA%\npm\node_modules\pyright\index.js`.

Путь к Node задаётся полем `nodePath`, по умолчанию берётся `node` из `PATH`. Если путь в
`pyrightPath` указан, но файла нет, кокпит не уходит молча в автопоиск, а сообщает об этом.
Отсутствие Node.js — штатное состояние: панель работает без него и пишет, почему pyright не
запускался.

**Конфигурация.** `pythonVersion "2.7"` использовать нельзя: pyright такое значение принимает,
но стабы Python 2 из typeshed давно удалены, и пропадают все встроенные имена (даже
`isinstance`). Рабочая связка — `pythonVersion 3.8` + `typeCheckingMode "off"` + `extraPaths`
на дерево исходников клиента: она даёт сигнал без шума на коде Python 2. В режиме `basic`
на эталонном моде появляются диагностики, и все они ложные — это правила Python 3 на коде
Python 2.

**Что отсеивается заведомо.**

- Имена Python 2 (`unicode`, `basestring`, `xrange` и другие) — в `reportUndefinedVariable`.
- Импорты API чужих модов (`gui.modsListApi`, `gui.modsSettingsApi`). Этих модулей в клиенте
  нет, а рецепты потому и импортируют их под `except ImportError`. Заглушка `.pyi` тут не
  годится: `gui` в клиенте — настоящий пакет, и пакет-заглушка `gui/` заслонил бы его
  целиком. Настоящий риск такого импорта разбирает правило `WOT018`.
- Собственный пакет мода. `import gui.mods.<пакет>` в игре работает (движок монтирует
  `scripts/client` из архива мода), а pyright его не резолвит: он находит `gui` в дереве
  клиента и в каталог мода уже не заглядывает. Поэтому список модулей мода собирается
  обходом проекта и передаётся в разбор. Гасится только доказанное: опечатка в имени модуля
  остаётся находкой.

**Две защиты от молчаливого «замечаний нет».** pyright игнорирует абсолютные пути в
`include` и анализирует ноль файлов, отвечая «замечаний нет», поэтому каталоги передаются
аргументами командной строки. А `filesAnalyzed == 0` считается **отказом**, а не успехом:
зелёный отчёт о непроверенном коде хуже отсутствия отчёта.
