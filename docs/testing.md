# Тесты

[← к README](../README.md)

## Как запустить

```powershell
dotnet build
dotnet test
```

Обычный `dotnet test` **герметичен**: он не читает ни установку игры, ни ваши проекты модов,
ни дерево исходников клиента, ни корпус чужих модов, ни файлы в `%APPDATA%`. Тесты, которым
всё это нужно, пропускаются с понятной причиной. Настройки кокпита на время прогона уводятся
во временный каталог (`TestSettingsIsolation` задаёт `WOTCOCKPIT_SETTINGS_DIR`, даже если
переменная уже была задана, например для второй копии кокпита), так что ваш `settings.json`
тесты не читают и не перезаписывают. В этом каталоге сразу лежит пустой `settings.json`:
загрузка настроек в тестах не пробует машину (поиск игры, шаблона, дерева исходников), как
это делает первый запуск кокпита. Сборки шаблона в тестах получают `--game-dir` с пустой
временной «игрой», а импорт дизайнера настроек читает фикстуру, а не `modsettings.dat`.

Тесты на шаблон мода и на Python идут и в обычном прогоне, если шаблон и Python найдены, и
пропускаются, если нет. Совсем без внешних зависимостей:

```powershell
dotnet test --filter "Env!=RealMachine&Needs!=Template&Needs!=Python"
```

Перед сборкой закройте запущенный кокпит: он держит
`src\WotModCockpit.App\bin\Debug\net8.0-windows\WotModCockpit.App.exe`, и `dotnet build`
падает с MSB3027/MSB3021.

**Концы строк.** `.gitattributes` держит текстовые файлы в LF на любой машине, независимо
от `core.autocrlf`: тесты хранят фикстуры Python в сырых строках C#, и с CRLF-копией часть
из них падала бы. Если клон был сделан до появления `.gitattributes`, сделайте свежий
checkout.

## Метки тестов

| метка | что значит |
|---|---|
| `Env=RealMachine` | тест читает файлы вашей машины (игру, свои проекты, дерево исходников клиента, `%APPDATA%`); включается переменной `WOTCOCKPIT_REAL_MACHINE=1` |
| `Env=DocScreenshots` | снимки окон для документации; включается переменной `WOTCOCKPIT_DOC_SCREENSHOTS` |
| `Needs=Template` | нужен шаблон мода `wot-mod-template` (его `build.py` и `tools/check_py2_syntax.py`) |
| `Needs=Python` | нужен Python 3 (тесты берут тот же, что `WOTCOCKPIT_PYTHON` или автопоиск кокпита, а не первый `python` из `PATH`) |
| `Needs=ClientSource` | нужно дерево исходников клиента |
| `Needs=ModCorpus` | нужен корпус распакованных сторонних модов |

Метки работают в фильтрах `dotnet test --filter`, например `--filter "Env!=RealMachine"`
или `--filter "Needs=Template"`. Метки ставятся по тому, что тест реально читает и
запускает: тест на дереве исходников клиента несёт и `Env=RealMachine`, и
`Needs=ClientSource`, тест на настоящем шаблоне с запуском `build.py` — `Needs=Template` и
`Needs=Python`.

Тест, которому чего-то не хватает, **пропускается** с причиной (`[SkippableFact]`), а не
притворяется пройденным и не падает. Даже с `WOTCOCKPIT_REAL_MACHINE=1` тест пропускается,
если нужного ресурса на машине нет.

## Переменные окружения для тестов

| переменная | что задаёт | по умолчанию |
|---|---|---|
| `WOTCOCKPIT_REAL_MACHINE` | `1` (или `true`) включает тесты `Env=RealMachine`; одно правило на все тесты | выключено |
| `WOTCOCKPIT_GAME_DIR` | каталог игры (где `paths.xml`); тесты его только читают | при `REAL_MACHINE=1` — игра, которую находит сам кокпит |
| `WOTCOCKPIT_REPOS_DIR` | каталог со своими проектами модов: проектом считается подкаталог с `build.py` и `src\` | родитель найденного шаблона (только при `REAL_MACHINE=1`) |
| `WOTCOCKPIT_TEMPLATE_DIR` | каталог `wot-mod-template` (его же читает сам кокпит) | соседний с кокпитом каталог `wot-mod-template*` |
| `WOTCOCKPIT_CLIENT_SRC` | дерево исходников клиента | `<шаблон>\.scratch\wot-src` (только при `REAL_MACHINE=1`) |
| `WOTCOCKPIT_CLIENT_SRC_VERSION` | версия этого дерева, если у него нет отметки `.cockpit-client.json` и версия не видна из имени `wot-src-<версия>` | — |
| `WOTCOCKPIT_MOD_CORPUS_DIR` | корпус распакованных и декомпилированных сторонних модов, по подкаталогу на мод | `<шаблон>\.scratch\mod-corpus` (только при `REAL_MACHINE=1`) |
| `WOTCOCKPIT_PYTHON` | Python 3 для тестов | автопоиск, как у кокпита |
| `WOTCOCKPIT_SETTINGS_DIR` | каталог `settings.json` (и журнала `mods-operations.log`) | всегда временный каталог прогона — заданное до прогона значение заменяется; при `REAL_MACHINE=1` не трогается |
| `WOTCOCKPIT_DOC_SCREENSHOTS` | папка для снимков окон документации | — (тесты снимков пропускаются) |
| `WOTCOCKPIT_DOC_DENYLIST` | личный стоп-список слов для снимков (по слову в строке): имена модов вашей машины, которых не должно быть в кадре; в репозиторий не кладётся | `<папка снимков>\.screenshot-denylist.txt`, если есть |
| `WOTCOCKPIT_TEST_SNAPSHOTS` | папка, куда тесты диалогов сетапа и перехода сохраняют картинку окна, чтобы посмотреть вёрстку глазами | — |

Дочерние процессы Python в тестах всегда запускаются с `PYTHONIOENCODING=utf-8` и
`PYTHONUTF8=1`, поэтому набор проходит и на Windows с нерусской локалью.

## Тесты на своей машине

С `WOTCOCKPIT_REAL_MACHINE=1` тесты читают установленную игру, ваши проекты модов, дерево
исходников клиента, корпус модов и `modsettings.dat` игрока. Всё это — **только чтение**:
там, где это важно, размер и время правки файла сверяются до и после.

```powershell
$env:WOTCOCKPIT_REAL_MACHINE = "1"
$env:WOTCOCKPIT_CLIENT_SRC_VERSION = "1.44"   # если у дерева нет отметки версии
dotnet test tests/WotModCockpit.Tests/WotModCockpit.Tests.csproj
```

**Эталонные числа.** Часть тестов индекса и каталогов сверяет точные числа (файлов, `def`,
событий, сервисов), снятые на дереве клиента **1.44**. На дереве другой версии такие тесты
пропускаются с причиной «дерево клиента не 1.44 — эталонные числа не применимы», а
проверки, не зависящие от версии (дерево разбирается, пороги, первые попадания поиска), идут
на любом дереве. Версию дерева без отметки задаёт `WOTCOCKPIT_CLIENT_SRC_VERSION` (или
отметка `.cockpit-client.json` вида `{"version":"1.44.0.0"}` в корне дерева).

**Корпус модов** — распакованные и декомпилированные чужие моды для проверки preflight на
ложные срабатывания. Это чужой код, в репозиторий он не входит, и скрипта для его сборки в
репозитории тоже нет. Пороги этих тестов сняты на конкретных версиях модов клиента 1.44,
поэтому им нужно и эталонное дерево 1.44.

## Снимки окон для документации

Картинки в `docs/*.png` снимаются тестами `DocScreenshotTests` с настоящей разметки и
настоящих моделей, но на **выдуманных данных**. Во временной папке строится фейковая машина
(`Games\Tanki`, `Users\dev\repos`, `Users\dev\wot-src`): три проекта `ru.example.*`, выдуманные
чужие моды, синтетический `python.log`, крошечное синтетическое дерево «исходников клиента»,
написанное прямо в тесте, и фикстура `Resources/modsettings.sample.json`. Настоящая игра и
`%APPDATA%` не читаются.

Перед каждым снимком корень временной папки в видимом тексте заменяется на `C:`, а после —
весь видимый текст окна проверяется. Абсолютный путь вне нейтральных корней (`C:\Games\Tanki`,
`C:\Users\dev`, `C:\Python312`), временная папка, путь профиля, имя пользователя или машины,
имя настоящего мода роняют тест, и картинка не пишется.

Пересоздать снимки (PowerShell, из корня репозитория):

```powershell
$env:WOTCOCKPIT_DOC_SCREENSHOTS = "$PWD\docs"
dotnet test tests/WotModCockpit.Tests/WotModCockpit.Tests.csproj --filter "FullyQualifiedName~DocScreenshotTests"
```

Фильтр `--filter "Env=DocScreenshots"` тоже работает. Прогон перезаписывает 11 PNG и
занимает порядка десятка секунд. Тестов три: `MainWindow_AllScreens` (главное окно на всех
экранах и подтверждение «Выключить мод»), `SetupBundleDialog_Shot` и
`ClientMigrationDialog_Shot`.

Для `mods-confirm.png` нужен интерактивный рабочий стол: настоящее системное окно
подтверждения появляется примерно на секунду, снимается и закрывается кнопкой «Нет». Без
рабочего стола этот шаг пропускается, когда остальные картинки главного окна уже записаны.
Без переменной все три теста пропускаются с причиной «снимки окон для README пишутся только
по переменной WOTCOCKPIT_DOC_SCREENSHOTS=<папка>».

## Что и как проверяют тесты

Общий принцип: проверяется **результат на настоящих данных**, а не факт вызова метода.

**Разметка и окна.**

- Разметка экранов загружается в настоящем окне с боевыми словарями ресурсов, а протокол
  привязок WPF пишется в список, и любая ошибка привязки роняет тест (`ApiBrowserViewTests`
  и другие тесты коллекции `WpfBindingTrace`). Неизвестный `{StaticResource}` — это
  `XamlParseException` при загрузке окна, то есть падение приложения на старте, а компилятор
  о нём молчит.
- Прокрутка к строке объявления проверяется по видимым строкам документа: `ScrollToLine` у
  AvalonEdit сам по себе ничего не гарантирует, WPF обновляет смещение только на следующем
  проходе разметки.
- Геометрия: кнопки действий панели Problems видны при штатной высоте дока
  (`ProblemsViewTests`), правая кнопка мыши в списке модов сначала выделяет строку
  (`ModsViewTests`), скругление углов собственной рамки проверяется по отрисованным пикселям
  (`ChromeWindowTests`).
- `WpfHost` держит один `Application` на процесс, `UiThread` — STA-поток с живым
  `Dispatcher`, без которого не тикает `DispatcherTimer`.

**Браузер API.** Экран целиком проверяется поверх настоящего шва Core
(`ApiBrowserRealBackendTests`): тест пишет во временный каталог маленький, но настоящий дамп
клиента и гоняет по нему живую модель экрана. Подставной бэкенд отвечает одинаково и на
`update`, и на `Foo.update`, поэтому без такого теста незаметной осталась бы панель «где
вызывается», которая на настоящем дереве отвечала «ссылок не найдено». На дереве вашего
клиента (`Env=RealMachine`) каждая подтверждённая запись каталога патчей обязана дать хотя
бы одно попадание.

**Preflight, рецепты, мастер.**

- `ReferenceTemplate_ProducesNoErrors`: эталонный шаблон мода чист — ноль ошибок и ноль
  предупреждений. Главный тест на ложные срабатывания.
- `RealCore_Preflight_FindsViolationsInBrokenMod`: мод из настоящих нарушений даёт непустой
  список находок с непустым «почему это плохо». «Шов подключён, но всегда пусто» выглядит в
  приложении так же, как «замечаний нет».
- Рецепты гоняются через `check_py2_syntax.py` все 16, трижды: как есть, после подстановки
  паспорта и на экзотическом имени пакета.
- `Created_Project_Builds_RealMtmod`: мастер собирает то, что создал (`build.py --clean`,
  проверка `.pyc` по magic-числу, в архиве нет старых имён).

**Дизайнер настроек.**

- `Container_ResolvesCoreGenerator`: из боевого контейнера приходит генератор Core, а не
  встроенная заглушка (заглушка тоже порождает рабочий код, и подмену видно только так).
- Сгенерированный код проходит `check_py2_syntax.py` и собственный preflight без находок.
- `Regeneration_KeepsHandWrittenTail`: дописанное ниже маркера переживает перегенерацию.
- `EverySampleTemplate_SurvivesTheSeam`: все шаблоны фикстуры `modsettings.sample.json`
  переживают шов «JSON → экран → Core». С `WOTCOCKPIT_REAL_MACHINE=1` то же проверяется на
  вашем `modsettings.dat` (`EveryLiveTemplate_SurvivesTheSeam`), а
  `SampleFixture_CoversLiveFileStructure` проверяет, что фикстура покрывает все ключи и типы
  вашего файла.

**Экран «Моды».** Тесты идут на фейковом каталоге игры во временной папке, и интересны в них
запреты:

- снимок каталога (путь, размер, sha256, время записи) сверяется при старте модели экрана,
  после первого чтения и после каждого отказа;
- путь вне каталога модов отвергается — и прямой, и через `..`, и через каталог-однофамилец
  `mods\<версия>-backup`;
- при запущенной игре (подставная проба процессов) команды экрана мертвы, а принудительный
  вызов в обход кнопки не меняет ни байта;
- удаление не происходит от одного щелчка: отдельные тесты на отказ в первом диалоге, на
  отмену ввода имени и на неверно напечатанное имя, плюс тест на удачный путь;
- круг «выключить → включить» через кнопки дважды подряд: файл на месте, sha256 тот же,
  каталог совпадает со снимком; выключенный файл исчезает из перечисления `*.mtmod` тем же
  способом, которым его видит движок;
- на настоящем каталоге игры (`Env=RealMachine`) — только чтение.

Тесты сетапа и перехода на новую версию клиента описаны в [Сетапе](setup-bundle.md) и
[Переходе на новую версию клиента](client-migration.md).
